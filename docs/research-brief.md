## 1. UEFN Python status in current release

- **Feature exists, embedded Python 3.11, framed as "early preview."** Epic's own doc literally says "an early preview" and warns "the UEFN Python API might change between releases." [dev.epicgames.com/documentation/fortnite/python-tools-in-uefn](https://dev.epicgames.com/documentation/fortnite/python-tools-in-uefn) — **CONFIRMED**
- **Underlying plugin lineage is Engine/Plugins/Experimental/PythonScriptPlugin**, carrying Epic's own "Beta... use caution when shipping" warning. [dev.epicgames.com/…/PluginIndex/PythonScriptPlugin](https://dev.epicgames.com/documentation/unreal-engine/API/PluginIndex/PythonScriptPlugin?lang=en-US) — **CONFIRMED**
- **Introduced ~v40.00**, sourced only to a non-Epic partner-account X post, not an official Epic page — treat version number as directionally right, not Epic-attested. [x.com/SupremeUEFN/status/2034553697422962771](https://x.com/SupremeUEFN/status/2034553697422962771) — **CONFIRMED (weak/single-source)**
- **Current live UEFN as of 2026-07-15 is v41.10** (released 2026-06-25); no Python-specific changes found in notes through 41.10, v41.20 imminent (~2026-07-16). No source found.
- **"Just check the Project Settings box" is stale/incomplete for current release.** Multiple concurrent 2026 Epic Developer Community forum threads report Python additionally gated by an **account-level allowlist** on top of the checkbox — console logs `LogPython: Python disabled via CVar 'Engine.Python.IsEnabledByDefault'`, and the checkbox itself may not even appear for un-allowlisted accounts; .ini overrides don't bypass it. Epic's own doc page is silent on this gate. Forum thread: [Python Editor Scripting Beta Access for UEFN MCP Integration](https://forums.unrealengine.com/t/python-editor-scripting-beta-access-for-uefn-mcp-integration/2730953) — **REFUTED-corrected**: verify locally on Mango's actual install (Output Log immediately after ticking the plugin) before assuming Python runs at all; if the CVar message appears, this whole tool is blocked pending Epic allowlisting, not a code problem.
- **Execution model**: Output Log console has two modes — Python mode (true line-by-line REPL, Shift+Enter for multi-line blocks) and default Cmd mode (`py "path/script.py" [args...]` runs a file, with `sys.argv` support for passed arguments — confirmed by Epic's generic doc phrasing "the rest of the line is executed by Python… exactly as if you had typed it into the Python console"). A "Tools > Execute Python Script" menu item is also available (per third-party corroboration). [dev.epicgames.com/…/scripting-the-unreal-editor-using-python](https://dev.epicgames.com/documentation/en-us/unreal-engine/scripting-the-unreal-editor-using-python) — **CONFIRMED**. Build the tool as a **saved .py file**, run via `py` or the menu item — never hand-type into the console.
- **No documented interactive `input()` support** anywhere in either doc — design around non-interactive flags/config + printed dry-run preview, not runtime prompts. No source found confirming or denying blocking-stdin support either way.
- **Enforcement is at validation/publish time, not API-call time**: writing a property not visible in the UEFN UI "will fail validation"; placing content not visible in content browsers/asset pickers "will also fail validation"; modifying non-allow-listed properties "will fail validation." This is a post-hoc gate, not a call-time exception — Epic explicitly recommends "Validate your content changes often." [dev.epicgames.com/documentation/fortnite/python-tools-in-uefn](https://dev.epicgames.com/documentation/fortnite/python-tools-in-uefn) — **CONFIRMED**. Our tool only moves/renames/deletes path metadata (not properties), so it should stay inside this wall — but test after every batch.
- Epic explicitly instructs: **"Never use file management modules built into Python… do not use `os.rename` or `shutil.move`"** — always route through `unreal.EditorAssetLibrary`/`AssetToolsHelpers`. Same source — **CONFIRMED**.
- Enabling Python triggers a pop-up for collaborators who open the project afterward, and Epic recommends pairing with source control (Unreal Revision Control) specifically to protect against scripting mistakes. Same source — **CONFIRMED** (secondary, non-load-bearing).

## 2. The correct asset-move recipe

**THE recommended approach: loop `EditorAssetLibrary.rename_asset()` per-asset (not `rename_directory`, not raw `AssetTools.rename_assets` unless you need its batch semantics and are careful with argument order), verify post-condition with `does_asset_exist`, and always run inside per-asset try/except.**

- `unreal.EditorAssetLibrary.rename_asset(source_asset_path, destination_asset_path) -> bool` — official docstring, word for word: **"Equivalent to a Move operation. Will try to checkout the file. The Asset will be loaded before being renamed."** Takes a full destination *object* path, not just a folder. Identical semantics on `EditorAssetSubsystem`. [EditorAssetLibrary docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/EditorAssetLibrary?application_version=5.5) — **CONFIRMED** (adversarially verified 3x, verbatim match).
- `rename_directory()` is the folder-bulk equivalent by doc wording, but is **reported broken in UE 5.1** per an Epic forum thread with no confirmed fix; community workaround is to list_assets() the source dir and loop rename_asset per item instead. [forums.unrealengine.com — Rename Directory function no longer works in 5.1](https://forums.unrealengine.com) — no independent adversarial vote run on this specific sub-claim, treat as unverified-but-plausible; **prefer per-asset rename_asset over rename_directory regardless.**
- `unreal.AssetToolsHelpers.get_asset_tools().rename_assets(assets_and_names: Array[AssetRenameData])` internally routes through `FAssetRenameManager::RenameAssetsAndVariants()` → `FixReferencesAndRename()` → `CheckOutPackages()` — the **same C++ pipeline the Content Browser's own right-click Rename/drag-move uses**, per an Epic engineer (LVL102) confirming the hardcoded checkout behavior is intentional, not a bug. [forums.unrealengine.com — RenameAssets()/FixupReferencers() hard-coded checkout](https://forums.unrealengine.com/t/renameassets-and-fixupreferencers-hard-coded-source-control-checkout/2673153) — **CONFIRMED** for the mechanism claim, but this thread is about the general engine C++ pipeline (Oct 2025, 3 posts, no UEFN/version number, never explicitly ties the Content Browser UI action to this exact code path — that link is *inferred* by the forum poster's context, not asserted outright). Treat "same pipeline as manual rename" as **plausible, not Epic-stated**.
- **`unreal.AssetRenameData` has a genuine argument-order trap**: documented *properties* list as `asset`, `new_name`, `new_package_path`, but the documented *constructor* signature is `AssetRenameData(asset, new_package_path, new_name)` — new_name and new_package_path are swapped between properties-order and constructor-order. Writing `AssetRenameData(asset, new_name_val, new_folder_val)` positionally silently swaps destination folder and new name. [AssetRenameData docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/AssetRenameData?application_version=5.5) — **CONFIRMED** (adversarially verified 3x, exact constructor dump matched). **Always use keyword args**: `unreal.AssetRenameData(asset=obj, new_package_path=folder, new_name=name)`.
- `rename_assets()`'s docstring is **silent on redirector behavior** ("Renames assets using the specified names." — that's the entire docstring). [AssetTools docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/AssetTools?application_version=5.5) — **CONFIRMED**.
- `rename_assets_with_dialog()` is the only dialog variant; unsuitable for a headless/scripted batch tool (blocks on UI). — **CONFIRMED** (existence of method + naming-convention inference; exact blocking behavior not independently doc-quoted, treat as high-confidence inference not literal quote).
- A real-world forum thread ("Failed to rename assets using Python") shows `AssetToolsHelpers.rename_assets()` throwing data-validation errors on some rename edge cases, and that **periods in names are rejected** ("Unreal does not like periods in names"), unresolved by Epic. — **Validate names (no illegal chars, no periods) before calling any rename API.**
- **Soft references are NOT reliably fixed by rename/redirector alone.** Use `unreal.AssetTools.rename_referencing_soft_object_paths(packages_to_check, asset_redirector_map)` separately — official docstring: "renames all FSoftObjectPath object[s] with the old asset path to the new one." Build one old→new map for the whole batch, load all potentially-referencing packages, call once at the end. — **CONFIRMED** (present on official docs).
- **Pre-move safety check**: `unreal.EditorAssetLibrary.find_package_referencers_for_asset(asset_path, load_assets_to_confirm=False) -> Array[str]` — only considers soft+hard deps, and **"Package dependencies are cached with the asset. False positive can happen until all the assets are loaded and re-saved."** [EditorAssetLibrary docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/EditorAssetLibrary?application_version=5.8) — **CONFIRMED** (adversarially verified 3x, verbatim). Surface this caveat to the user in the dry-run preview — don't treat the referencer count as ground truth.
- `delete_asset()`/`delete_directory()`/`delete_loaded_asset(s)` are all **Force Delete**: "doesn't check if the assets have references in other Levels or by Actors," closes open editors, "**may clear the Transaction buffer (Undo History)**." [EditorAssetLibrary docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/EditorAssetLibrary?application_version=5.8) — **CONFIRMED** (adversarially verified 3x, verbatim). This is why the tool needs its **own external undo log** (JSON record of source→dest moves) — editor Ctrl+Z is not reliable across these calls.
- `save_asset`/`save_loaded_asset(asset, only_if_is_dirty=True)` — save only dirty packages touched by the run, don't blanket-save the whole project.
- `consolidate_assets()` is a merge/dedupe primitive (many-old-names → one survivor, deletes originals, **leaves redirectors**) — not a like-for-like move tool, not needed for core organizing, only relevant if prefix-rename ever needs to collapse name collisions.

## 3. Redirector cleanup from Python

**Bottom line: there is no Epic-shipped Python method to fix up redirectors. Every programmatic rename/move leaves one — this is not optional cleanup, it's required or `/Game/` (or the project-name root) fills with orphan `ObjectRedirector` assets.**

- `unreal.AssetTools`/`AssetToolsHelpers.get_asset_tools()` does **not** expose `fix_up_redirectors`, `fixup_referencers`, or any redirector-cleanup entry point in any version checked (5.2 through 5.8). Full method list confirmed empty of this capability. — **CONFIRMED** (adversarially verified 3x against live docs across multiple engine versions).
- The real function, `IAssetTools::FixupReferencers(...)`, is **C++-only** — never marked `UFUNCTION(BlueprintCallable)`, so the Python auto-binding layer never picks it up. Epic forum: original ask 2019, reconfirmed "no direct Python API exists… requires C++ plugin development" June 2024. [forums.unrealengine.com — Python scripting to fix up redirectors in a folder?](https://forums.unrealengine.com/t/python-scripting-to-fix-up-redirectors-in-a-folder/125267) — **CONFIRMED**.
- **All community workarounds require a compiled custom C++ plugin** (e.g. `revoconner/Fixup-Redirector-Unreal` exposing `unreal.RedirectorFixerBPLibrary.fixup_referencers()`, or the paid TAPython plugin's `PythonBPLib.fix_up_redirectors_in_folder()`) — **irrelevant for us: UEFN is a locked/precompiled engine build, no custom native C++ module can be installed.**
- **The stdlib+unreal-only recipe that actually works**, reverse-engineered from Epic's own description of what the manual "Fixup" context-menu action does ("resave all packages that point to the redirector, and delete the redirector if it was able to resave all things referencing it" — [dev.epicgames.com/…/asset-redirectors-in-unreal-engine](https://dev.epicgames.com/documentation/unreal-engine/asset-redirectors-in-unreal-engine?lang=en-US)):

```python
import unreal
eal = unreal.EditorAssetLibrary

def find_redirectors(root):
    return [p for p in eal.list_assets(root, recursive=True, include_folder=False)
            if eal.find_asset_data(p).is_valid() and eal.find_asset_data(p).is_redirector()]

def fixup_redirector(redirector_path):
    referencers = eal.find_package_referencers_for_asset(redirector_path, True)  # load_assets_to_confirm=True
    for ref_path in referencers:
        obj = eal.load_asset(ref_path)
        if obj:
            eal.save_loaded_asset(obj, only_if_is_dirty=False)
    remaining = eal.find_package_referencers_for_asset(redirector_path, False)
    if not remaining:
        eal.delete_asset(redirector_path)
        return True
    return False
```
This is inferred/self-authored from documented primitives, not itself an Epic-shipped call — **CONFIRMED as the correct composition of documented pieces**, but **UNTESTED in a live UEFN session** (see Section 7).

- **Scope and throttle, never sweep the whole project at once.** `revoconner/Fixup-Redirector-Unreal`'s own fixup.py explicitly warns "loading with unloaded assets will cause you a world of pain" and to "choose only the root folder of the redirectors, not `/Game/`" — batches of default size **1**, with 2.0s delays between batches, 0.5s between items, doubling delay on error, plus `unreal.SystemLibrary.collect_garbage()` between batches. Mirror this: fixup redirectors **scoped per-move-batch immediately after that batch**, not as a project-wide sweep.
- **Commandlet alternative flagged unusable for UEFN**: `UnrealEditor(-Cmd).exe <project> -run=ResavePackages -fixupredirects -autocheckout -projectonly -unattended` must run as a **separate OS process** against the `.uproject` — UEFN doesn't launch that way (it's wrapped by the Fortnite/Epic launcher), so reachability for a UEFN project is **unconfirmed by any source found**. Document it in the tool's own docs as an unsupported fallback for full desktop UE5 only, not something to promise for UEFN.
- **Do not promise "auto-clean redirectors" as a hard guarantee.** Frame as: best-effort fixup for redirectors whose referencers are all loadable/resavable in-session, plus an explicit **flagged remainder list in the summary log** for anything still referenced or that failed — matching what the real-world `EDMIRE2k/UEFNContentBrowserOrganizer` tool does (it doesn't auto-fixup at all; it requires the user to manually right-click "Update Redirector References" after every run). [github.com/EDMIRE2k/UEFNContentBrowserOrganizer](https://raw.githubusercontent.com/EDMIRE2k/UEFNContentBrowserOrganizer/main/README.md) — **CONFIRMED**.

## 4. UEFN-specific traps

- **Content root is NOT reliably `/Game/`.** UEFN projects mount as their own content plugin; the canonical Epic-documented getter is `unreal.EditorAssetLibrary.get_project_root_asset_directory()`, whose own docstring states: *"Historically, all project assets were stored in the logical '/Game/' directory when using plugins or UEFN projects, we want to ease asset reuse, and so the ambiguous '/Game/' directory is untenable. This function will return the useful project name"* — returns the **project name** in UEFN, `/Game/` only as a `.uproject` fallback. [EditorAssetLibrary docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/EditorAssetLibrary?application_version=5.5) — **CONFIRMED** (adversarially verified 3x, verbatim, cross-corroborated by a live third-party MCP tool independently deriving the same `/{ProjectName}/` root from `world.get_path_name()`). **Resolve the root at runtime via this call — never hardcode `/Game/`.** Note the same third-party repo is internally inconsistent (some of its own tool defaults still hardcode `/Game/`) — a warning to design our own tool more carefully, not evidence against the core fact.
- **`.verse` source files are entirely outside the Python asset API.** They live in a separate system (Verse Explorer), are not tracked in the Asset Registry, and no source (official or community) describes any Python binding for scanning/moving/renaming raw `.verse` text files — confirmed by exhaustive negative-space checking (Epic docs silent, EditorAssetSubsystem/EditorAssetLibrary reference pages describe only Asset-Registry-backed objects, a real UEFN organizer tool's code never mentions Verse). — **CONFIRMED**. **Exclude `.verse` files entirely from the tool's scan/move/rename pipeline.** Only *compiled* Verse device/class objects (generated after a Verse build) show up as real Content Browser assets and are movable normally.
- **Moving an asset that's Verse-exposed (via Asset Reflection) is not reference-safe the way a normal asset move is.** Verse identifiers are plain-text symbols regenerated on next build (e.g. an asset in a "Meshes" folder becomes `Meshes.MySphere` in Verse code) — the asset-move APIs fix up references *inside the asset system* (redirectors) but there's **no evidence they rewrite existing Verse source code** referencing the old qualified name. No source directly confirms or denies breakage; this is an inference from how Asset Reflection is documented to work, not independently tested. Treat as a **strong caution, not a confirmed bug**: heuristic-flag "project has 1+ .verse files" as a signal to warn more loudly before moving assets, and never move assets without explicit confirmation if Verse exposure is plausible.
- **Protected/system folders** — `__ExternalActors__`, `__ExternalObjects__`, `__ExternalMetadata__` (OFPA/World Partition auto-generated, GUID/hash-addressed, should never be manually reorganized) and anything containing `.umap` files (levels) — this is inferred from **general UE/OFPA documentation, not a UEFN-specific Epic statement**. No source found saying Epic explicitly warns against this in UEFN. **Hard-exclude these path segments by default (user-editable, defaulted ON), and flag in the tool's own docs that this is an inferred-safe-default, not an Epic-confirmed rule.**
- **`unreal.SystemLibrary.get_system_path()`** is the correct/only robust way to go from an asset package path to a real disk path — don't hand-roll path conversion (double-extension naming plus per-type disk extensions like `.uasset`/`.umap` make manual conversion error-prone). No direct adversarial vote run on this specific sub-claim; treat as plausible, standard UE guidance.
- **Project name / content dir getters**: `unreal.SystemLibrary.get_project_content_directory()`, `get_project_directory()`, `get_project_saved_directory()` (good place for dry-run/summary/undo log files — already gitignored/transient by convention), `get_game_name()` (the real "project name" getter — no `get_project_name()` exists). `unreal.Paths.project_content_dir()`/`project_saved_dir()` etc. give overlapping values as engine-relative strings — normalize with `os.path.normpath` before display. No adversarial vote run on these specific sub-claims; standard, low-risk API surface.

## 5. Dialogs / selection / progress APIs

- **`unreal.EditorDialog.show_message(title, message, message_type, default_value=..., message_category=...)`** returns `AppReturnType` — this is the real, native "Confirm Organize before executing" gate. `message_type` (e.g. `YES_NO`) controls buttons. **Caveat**: under `-unattended` command-line mode it no-ops and returns `default_value` immediately (irrelevant for a live editor session, relevant only if ever wrapped in a commandlet). Also available: `show_suppressable_warning_dialog` (good fit for a one-time redirector-cleanup caveat with a "don't show again" checkbox). No independent adversarial vote run on this class specifically, but it's a long-standing, stable part of Editor Scripting Utilities (same plugin family as the already-trusted `EditorAssetLibrary`) — **high-confidence, treat as CONFIRMED by association**.
- **`unreal.ScopedSlowTask(work, desc, enabled=True)`** — context-manager progress bar; `.enter_progress_frame(1, desc)` per item; `.make_dialog(can_cancel=False)` to actually pop the visible bar (otherwise it's a silent counter); `.make_dialog_delayed(delay, ...)` to avoid a UI flash on fast scans; `.should_cancel()` polled inside the loop lets a user abort a long batch mid-way — **exactly where the external undo-log matters**, since a cancel mid-batch leaves partial state. Same confidence tier as above — **treat as CONFIRMED by association**, not independently adversarially verified.
- **Selected-folder/asset APIs — CONTESTED, one specific claim REFUTED.** `unreal.EditorUtilityLibrary.get_selected_assets()`/`get_selected_asset_data()`/`get_selected_folder_paths()`/`get_selected_path_view_folder_paths()` are real, long-documented methods in the general UE Python API (Blutility module). But the adversarial check on "confirmed working in a live UEFN editor" came back **2-of-3 REFUTED**: the sole supporting source (a third-party MCP server repo) has a bare untested wrapper, its own "verified via live UEFN introspection" claims cite generated-doc artifacts that **don't exist in the repo** (maintainer's own open issue admits the generator "was never created"), and `EditorUtilityLibrary` belongs to the **Blutility (Editor Utility Widgets)** plugin — architecturally distinct from **Editor Scripting Utilities**, the plugin actually named by Epic's UEFN doc and confirmed to back `EditorAssetLibrary`/`AssetToolsHelpers`. A directly-comparable real UEFN organizer tool (`EDMIRE2k/UEFNContentBrowserOrganizer`) **avoids this API entirely**, using full asset-registry scanning instead — a real signal it may not be reliable in UEFN. — **REFUTED-corrected: do not assume this works. Test live first; fall back to an explicit user-supplied folder path (via the already-confirmed `list_assets(path)`) for the "sort only selected folder" bonus feature if selection reads fail or return empty.** Also note the documented papercut (in stock UE, unconfirmed for UEFN either way): `get_selected_folder_paths()` only catches asset-view folder-icon selections, while `get_selected_path_view_folder_paths()` (5.3+) is needed for left-tree/Sources-panel selections — call both and merge if you do end up relying on this.
- **tkinter — CONTESTED (split 1 confirmed / 1 refuted-but-reframed / 1 confirmed on independent re-verification).** A shipped UEFN organizer script does successfully use `tkinter`/`messagebox.askyesno` for a "Confirm Organize" dialog, and a third-party MCP server independently ships a persistent `tk.Toplevel`-based status window with an explicit code comment "two tk.Tk() crashes tcl" — real, working evidence tkinter functions inside UEFN's embedded Python on at least some installs. However, one reviewer correctly flags that the specific `get_tk_root()` helper is **not a tkinter/Epic API** — it's a private convenience function one particular third-party wrapper injects into its own exec namespace, not something that ships with UEFN or `unreal`. **Net guidance: tkinter is plausible but unofficial/unverified by Epic** (no mention anywhere in Epic's docs); if used, write your own single-root-reuse pattern (one `tk.Tk()` at module scope, `tk.Toplevel(root)` for anything after) rather than assuming a `get_tk_root()` helper exists. **Prefer `unreal.EditorDialog.show_message` for simple confirm/status dialogs** — it's native, documented, and can't collide with a second GUI toolkit's event loop.

## 7. Open unknowns needing runtime probing inside UEFN (honest gaps)

1. **Whether Python is actually usable on Mango's account/project right now.** The CVar-gate/allowlist issue (Section 1) is the single highest-priority thing to check before writing a line of tool code — check the Output Log immediately after enabling the plugin. No web source can settle this; it's account-specific.
2. **Whether the redirector-fixup recipe in Section 3 actually works end-to-end in a live UEFN session.** It's a correct composition of documented primitives, but nobody's shipped UEFN tool does full in-code redirector cleanup this way — every real-world precedent either requires a C++ plugin (impossible in UEFN) or punts to the manual right-click step. Test on a throwaway folder before trusting it in a real run.
3. **Whether `get_selected_assets()`/`get_selected_folder_paths()` work at all inside UEFN.** Actively refuted as "confirmed" by adversarial review — needs a direct in-console test (select something in the Content Drawer, run the call, log the result) before the "sort only selected folder" bonus feature can be built on it. Have a folder-path-argument fallback ready regardless.
4. **Whether `AssetTools.rename_assets()` hits the period/validation failures reported in the (non-UEFN) forum thread when run inside UEFN specifically**, and whether UEFN's separate allow-list validation layer adds its own additional rejection cases on top. Untested.
5. **Whether moving a Verse-exposed asset into a new folder actually breaks Verse compilation with no redirector protection**, as inferred from how Asset Reflection/qualified naming is documented — no direct test found either confirming or denying actual breakage. Needs a real test project with a Verse-exposed asset.
6. **Whether tkinter is reliably available/stable in the exact current-release (v41.x) embedded Python**, versus the March-2026-era evidence found. Given the "prefer native EditorDialog" fallback exists, this is low-risk to leave unresolved, but worth a 30-second smoke test.
7. **Exact underlying engine/Python minor-version behind UEFN v41.10** — no source pinned this; recommend `help(unreal.AssetTools)` in-console as a first step to see the live method surface rather than trusting any doc-version snapshot.
8. **Whether the `__ExternalActors__`/OFPA protected-folder exclusion list is complete/correct for UEFN specifically** — it's an inference from general UE World Partition docs, not a UEFN-confirmed list. If Mango's project structure differs, this default exclusion set may need adjusting.
9. **Whether UEFN's validation/publish step ever fires from a pure path rename/move (not a property write)** — theoretically no (path isn't a "property"), but no source explicitly confirms this negative for UEFN.
